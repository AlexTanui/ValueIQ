ValuIQ: valuing every flat in the City of Sydney

Intelligent Property Valuation Through Data. Microburbs Hackathon, Task 5 (Value Every Flat). Valuation date 31 August 2026.

ValuIQ estimates the 31 August 2026 sale value of every unit-style address in the City of Sydney. It values each flat from its own building's sales history, brought forward with a repeat-sales price index, and then adjusts for the unit's characteristics and location. Everything is built only from sales dated on or before the valuation date.

2. Held-out validation

We used a chronological split that mirrors the competition. The model, price index and every feature were built only from sales before 1 July 2026. They were then scored on unit sales from 1 July to 31 August 2026, which is the same 0–2 month horizon as the judging sales. Because the judging set uses flats under $1.2 million, the headline metric uses that subset.

3. The market: a repeat-sales price index

We matched consecutive sales of the same flat, 66,000+ pairs, and solved a quarterly Bailey–Muth–Nourse index with light smoothing. The index puts every historical sale on the same price footing, and it brings each flat's last sale forward to 31 August 2026. The index is rebuilt inside every validation fold from pre-cutoff sales only.

4. Method

Data and cleaning

  • Addresses: addresses from the Microburbs API across 29 suburbs. Of these, are unit-type addresses in buildings. Every address gets a value.
  • Sales: all unit sales from 1990 to 31 August 2026. We requested them with to_date=2026-08-31, so later sales were never downloaded, and we filtered them again after loading.
  • Bulk sales removed: whole-building or en-bloc transactions appear as the same price on the same day against many units, some above $600 million. Any price, date and location repeated across 3 or more units was dropped. Prices outside $100k–$20M were also dropped. clean unit sales remain.
  • Buildings: each address was split into a unit part and a street part, so 12/34 RALPH ST belongs to building 34 RALPH ST. Floor comes from the API's level field where present, otherwise from hundreds-style unit numbers (1205 → floor 12) in buildings with 20 or more flats.
  • Missing data: missing bedrooms, bathrooms and parking are kept as missing, never treated as zero. LightGBM learns from the missingness directly.

Features, all point-in-time

Each sale price is converted to an index-adjusted log price. Then, for every row, we summarise only the sales dated strictly before that row's information date. This applies to training rows too, so a 2018 sale only sees pre-2018 evidence. The features are:

  • the flat's own last sale (index-adjusted) and how long ago it was
  • building averages: all units, units with the same bedroom count, and the most recent sale in the building
  • mesh-block, 250 m grid-cell, suburb, and suburb × bedroom averages, each with its sale count
  • unit attributes: bedrooms, bathrooms, parking, flats in building, floor, unit number, dwelling type, and commercial or car-space flags
  • building age, using the first recorded sale as a proxy
  • location from OpenStreetMap: distance to the nearest train, metro or light-rail station, stations within 800 m, and distance to the harbour or water, parks and major roads

What drives the model (share of LightGBM gain, top 12)

The key step: value the building, then the unit

Most flats have not sold recently, but their building usually has. ValuIQ treats the building as the main unit of evidence. Every past sale in the building is brought to today's prices with the repeat-sales index and grouped by bedroom count. LightGBM then learns how much to trust this building evidence compared with the flat's own last sale, the neighbourhood, and the unit's own attributes. The building × bedroom average alone is the single most important feature.

Model

The model is LightGBM with a Huber loss on index-adjusted log price, so a few extreme sales can't dominate the fit. It uses 1,500 rounds, and sales from the last 3 years get double weight. To produce a value, we add back the index level at the valuation quarter and take the exponential.

5. What worked and what did not

  • Worked: point-in-time building × bedroom evidence was the biggest gain. LightGBM was stable across the three 2-month folds, with a mean within-10% of . OpenStreetMap location features added a small improvement.
  • Did not work: CatBoost with the same features was unstable, and some of its predictions blew up in one fold. A 50/50 blend with LightGBM was worse than LightGBM alone, so both were dropped. Simple last-sale indexing was capped at around 46% because many flats have no recent sale of their own.

6. Limitations

  • The supplied input file was not received, so the ID set comes from the Microburbs API's unit addresses. Running src/predict.py with the official input file restricts the output to exactly those IDs.
  • The bedroom, bathroom and parking values from the API reflect each address's most recent advert, and their source dates are not exposed. Validation uses the bedroom count recorded on each sale.
  • The holdout has a few hundred sales, so differences of about 2–3 points between models are within sampling noise.
  • Houses, shops and offices are valued with the same unit model and are likely less accurate. They are not part of the flat judging set.
